## Analysis

### Not a code regression (since last green run)

1. **CI is green.** The most recent CI run on `main` (commit `8dfeeb8`, 2026-07-31) passed all 4752 tests with zero failures.
2. **No PGlite test files changed recently.** The last modification to any file in `tests/pglite/` was commit `7e2a4d8` ("Fix closeFs to prioritize sync error over close error"), well before the last all-green run.
3. **No performance-affecting source changes since last green run.** The commits since the last report (`8dfeeb8`) are limited to the report itself — no source changes.
4. **Sibling tests in the same files pass.** For example, UPSERT Scenario 2 passes at cache=small (24s), cache=medium (12s), and cache=large (8s) — only cache=tiny (43s) times out. Similarly, GIN index passes at cache=tiny (28s, nearly borderline) but times out at cache=medium (43s).

### Root cause: fsync implementation made tests slower + tight global timeout

The deeper root cause is a **timeline mismatch**: the PGlite stress tests were created on June 9 (`7e2a4d8`), calibrated against MEMFS-like behavior where Postgres's `fsync(fd)` calls were silently no-ops. Three days later, real `fsync` was implemented:

- **Commit `27f86fd` (June 12)** — "Add fsync stream_op for per-file durability (#335)": `fsync(fd)` now flushes dirty pages to the backend and writes metadata. This is correct behavior (the prior no-op was a silent durability gap).
- **Commit `3404c4d` (July 7)** — "Make fsync atomic via syncAll instead of separate writes (#354)": Changed fsync from two separate calls to the more expensive `collectDirtyPagesForFile` + `syncAll` + `commitDirtyPages` pattern for atomicity.

Postgres calls `fsync` frequently — after WAL writes, during checkpoints, and during transaction commits. Under cache pressure (especially tiny/4-page cache), nearly every page access triggers an eviction and every `fsync` has dirty pages to flush.

### Why these 4 specific tests

The affected tests share I/O-intensive patterns amplified by fsync:

- **GIN index on tsvector (medium cache)**: GIN indexes create scattered page access (entry tree + posting lists + pending list). At 64 pages, the working set partially fits but GIN maintenance causes frequent cache thrashing with `to_tsvector` on 30 rows.
- **CASCADE DELETE (tiny cache)**: 20 parents × 5 children = 100 child rows. Cascade scans child indexes, deletes child/parent heap tuples — all competing for 4 cache slots. Every page access evicts a dirty page.
- **CASCADE UPDATE (medium cache)**: 15 parents × 4 children with CASCADE on a UNIQUE column. Each UPDATE rewrites child rows, touching both index and heap pages.
- **UPSERT with secondary index (tiny cache)**: 80 products × 2 rounds. Each UPSERT requires index lookup for conflict detection + insert/update + secondary price index maintenance. At 4 pages, extreme thrashing.

### Environment amplification

- The global `testTimeout` in `vitest.config.ts` is **30,000ms** with no per-file overrides in any PGlite test.
- This remote container is slower than CI's `ubuntu-latest` runners, pushing borderline tests past 30s.
- Vitest's thread pool (`pool: "threads"`) on limited cores adds parallel contention.
- One PGlite test file already accounts for this: `cache-pressure-persistence.test.ts` conditionally removes `@fast` for tiny cache with the comment: *"Tiny cache (4 pages) causes extreme thrashing during PGlite operations... This is inherently slow and cannot meet the @fast timeout."*

## Fix Plan

### Option A: Increase timeout for PGlite stress tests (recommended)

Add per-file timeout overrides to the 3 affected PGlite test files. This is the simplest, least-risky fix.

**Files to modify:**
- `tests/pglite/fts-gin-stress.test.ts`
- `tests/pglite/fk-cascade-stress.test.ts`
- `tests/pglite/upsert-trigger-stress.test.ts`

**Change:** Add a `beforeAll` or top-level vitest config override setting `testTimeout` to 60000ms (60s) in each file, or use `describe.each` with an explicit timeout parameter.

Example approach:
```ts
// At the top of the describe block:
beforeAll(() => {
  // PGlite stress tests spin up real Postgres WASM and can be slow
  // in constrained environments
}, 60_000);
```

Or, apply to the whole file via vitest's per-file config:
```ts
import { describe, it, expect } from 'vitest';

// Each test in this file gets 60s instead of the default 30s
describe('...', { timeout: 60_000 }, () => {
  // ...
});
```

**Pros:** Targeted fix, doesn't affect other tests, no risk of masking real regressions.
**Cons:** Doesn't address the underlying performance characteristic.

### Option B: Apply timeout to all PGlite tests via vitest workspace

Create a vitest workspace config that sets a higher timeout for all `tests/pglite/**` files.

**Pros:** Covers future PGlite tests automatically.
**Cons:** More structural change; vitest workspace config can be complex.

### Option C: Increase global timeout

Change `testTimeout` in `vitest.config.ts` from 30000 to 60000.

**Pros:** Simplest one-line fix.
**Cons:** Weakens timeout protection for all tests, could mask real hangs elsewhere.

### Option D: Reduce workload sizes in expensive variants

Reduce row counts in the most expensive test/cache-size combinations. For example, GIN Scenario 1 (medium cache) inserts 30 rows — reducing to 15-20 would cut runtime proportionally while still exercising GIN index patterns.

**Pros:** Directly reduces test runtime regardless of environment speed.
**Cons:** Reduces stress-test coverage; may miss edge cases that only appear at higher row counts.

### Recommendation

**Combine Options A and D.** Apply per-file 60s timeout to all 3 affected PGlite test files (Option A), and also follow the existing pattern from `cache-pressure-persistence.test.ts` by conditionally removing the `@fast` tag from the most expensive test/cache-size combinations (GIN medium, CASCADE tiny, UPSERT tiny) so they are excluded from smoke tests but still run in the full suite.

Consider Option D only if the timeouts continue to be borderline even at 60s on the slowest target environments.
